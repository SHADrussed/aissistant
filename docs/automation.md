# Автоматические проверки и развёртывание

`.github/workflows/ci.yml` запускается при push в `main`, в pull request,
по понедельникам в 06:17 UTC и вручную через **GitHub → Actions → CI → Run workflow**.
Расписание GitHub выполняется с возможной задержкой, а не с гарантией точного времени.
Если Actions отключён для репозитория, включите его в **Settings → Actions → General**.
Проверки расходуют минуты GitHub Actions в пределах тарифа владельца.

Сначала выполняются Ruff и полный набор тестов с одноразовым PostgreSQL 17.
После рестарта сервера отдельно проверяется доставка сохранённой очереди.
Затем собирается основной production `Dockerfile`; контейнер без сети проверяет
синтетические циклы, повторный запуск с сохранением состояния, миграцию, права,
блокировку второго worker и SIGTERM. API проверяются подменёнными transport,
а не личными аккаунтами. Никаких repository secrets для CI не требуется.

Workflow имеет только `contents: read`, checkout не сохраняет Git credentials.
Actions закреплены commit SHA. CI не пишет в репозиторий, не публикует образы,
не подключается к Railway и не исправляет ошибки самостоятельно. Он не использует
`pull_request_target` и не передаёт личные данные или runtime secrets в runner.
Еженедельный запуск проверяет текущий lockfile, но не обновляет зависимости.

## Связать Railway с результатами CI

1. В GitHub откройте последний commit в `main` и дождитесь двух зелёных jobs:
   **Python and PostgreSQL** и **Docker offline smoke**. При ошибке изучите
   соответствующий шаг в **Actions → CI**. Ошибка CI требует исправления кода.
2. В Railway откройте synthetic service → **Settings → Source**: проверьте
   репозиторий, ветку `main` и включённый автоматический deploy из GitHub.
3. В настройках GitHub source включите **Wait for CI**, если этот параметр доступен.
   Он должен задерживать deploy до успешного завершения GitHub checks.
   Если параметра нет, отключите автоматический deploy и запускайте deploy вручную
   только после зелёного CI. Сам `railway.toml` ожидание CI не включает.
4. Убедитесь, что выбран `Dockerfile`, одна реплика, постоянная БД/volume,
   `mode="synthetic"`, Telegram/Gmail выключены. Не добавляйте личные ключи ради CI.
5. После следующего обновления проверьте порядок: сначала зелёный CI, затем
   успешный Railway build и runtime `cycle_complete ... success=True`.
   При сохранённом состоянии повторный запуск должен иметь `sent=0`.

Не отключайте CI ради прохода ошибочной сборки. Расписание CI не должно
перезапускать работающий Railway service: еженедельный запуск не создаёт commit.
Мониторинг текущего состояния Railway и уведомления об авариях отдельно
настраиваются владельцем в Railway/GitHub; этот workflow их не заменяет.

## Границы автоматизации

Работающий секретарь сам выполняет цикл с интервалом `poll_seconds` (обычно 900).
В synthetic используются только встроенные вымышленные сообщения. Новые личные
источники подключаются по [инструкции](personal-authorization.md) с отдельным
подтверждением владельца, авторизация выполняется только на его устройстве.
Автоматических ответов собеседникам нет; бот предназначен для сводок владельцу.

Эта конфигурация не создаёт фонового Codex-агента. Самостоятельная разработка,
исправление ошибок и изменение production требуют отдельного механизма запуска
и согласованного объёма полномочий. Секреты не передаются в чат или GitHub Actions.
