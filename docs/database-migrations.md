# База данных и миграции

Поддержаны SQLite и PostgreSQL через psycopg; текущая Alembic revision —
`0002_monitoring` (v0.2). Worker применяет миграции при запуске под эксклюзивной блокировкой.
Это не полноценный механизм zero-downtime upgrades: перед будущими изменениями
схемы остановите worker и проверьте backup. Встроенный destructive downgrade запрещён.

## Начальная схема и существующий MVP

Новая БД получает `cursors`, `seen`, `outbox`, `alembic_version`. Старый MVP без
версии принимается только при совпадении всех трёх таблиц, столбцов, типов,
nullability и primary keys; данные не перезаписываются. Частичная/неизвестная схема
и версия новее/неизвестная текущему коду приводят к отказу, а не сбросу состояния.
Перед обновлением существующей БД всё равно создайте проверяемый backup.

SQLite `.backup`/backup API делается без сырых копий открытого файла. Для PostgreSQL
используйте провайдерский backup или `pg_dump` с секретами из доверенного env,
а не в argv. Backup содержит личные сводки и требует тех же мер защиты, что сама БД.

Для явного обслуживания есть команды (URL задаётся только в env):

```bash
uv run --frozen aissistant-db check
uv run --frozen aissistant-db upgrade
```

Обе требуют `MIGRATION_DATABASE_URL`; они не выбирают личную БД по умолчанию.
`check` ничего не мигрирует. Успех выводит только `{"revision":"0002_monitoring"}`,
ошибка — фиксированный `database_operation_failed`, без DSN/traceback/SQL values.
На Railway обычный старт не требует отдельного pre-deploy command. Для SQLite
pre-deploy environment может не иметь volume; миграция поэтому выполняется внутри
основного worker, после подготовки `/data` и получения блокировки.

## Одновременные worker и перезапуски

Одна реплика остаётся обязательной. SQLite использует OS flock рядом с каноническим
путём БД; PostgreSQL — session advisory lock, отдельный от таблиц, на сочетание
database/schema. Второй worker с той же БД отказывает до миграции/чтения источников.
Первый worker удерживает lock до завершения. При redeploy лучше явно остановить
старый worker; если новый наткнулся на lock, после остановки старого перезапустите
его в Railway. Ограниченное число restart attempts может быть исчерпано.

Потеря PostgreSQL lock connection приводит к остановке при следующей проверке;
lock проверяется перед циклом и перед карточками. Это защита от обычного overlap,
не distributed exactly-once: при сетевой неопределённости/принудительном убийстве
между send и commit дубликат карточки всё ещё возможен.

`seen` и outbox записываются одной транзакцией. Курсоры и pending payload живут в
БД, не в памяти контейнера. Смена машины/перезапуск не должны сбрасывать БД или
удалять volume. Исчезновение ephemeral `/data` без volume сбросит SQLite.

## Перенос SQLite → PostgreSQL

Это отдельная offline-операция **после решения владельца**, не автоматический этап
deployment. В этой задаче перенос проверяется только на синтетических данных.

1. Остановите **все** worker источника и цели. Заблокируйте autodeploy на время работ.
2. Сделайте и проверьте backup исходной SQLite. Примените `upgrade` к источнику,
   если он был ещё без Alembic version, затем `check`.
3. Создайте отдельную пустую PostgreSQL БД. Проверьте сетевой маршрут: private URL
   Railway работает из его private network; с личного устройства нужен защищённый
   маршрут/туннель. Не включайте публичный незащищённый PostgreSQL ради миграции.
   Для публичного TLS endpoint нужны реальные доверенные CA и hostname verification;
   не отключайте проверку сертификата и не предполагайте, что Railway Postgres
   изначально настроен принимать TLS на публичном TCP proxy.
4. В доверенном maintenance runtime задайте `MIGRATION_SOURCE_URL` (SQLite) и
   `MIGRATION_TARGET_URL` (пустая PostgreSQL), без значений в shell history.
5. Выполните:

   ```bash
   uv run --frozen aissistant-db copy --confirm-offline
   ```

6. Источник открывается read-only, целевая схема мигрируется, все целевые таблицы
   проверяются на пустоту **до записи**. Переносятся точные ключи/курсорные значения,
   seen, payload, created и delivered, включая pending и уже доставленные карточки.
   Количество и SHA-256 содержимого всех строк сверяются внутри target transaction;
   ошибка откатывает вставки. Выводятся только количества строк, не payload/DSN/digest.
7. Повторный запуск на непустой цели откажет. Не удаляйте таблицы для «повтора»:
   расследуйте причину на тестовой копии. Исходная SQLite остаётся неизменной.
8. После успешной проверки измените только runtime DB reference, запустите ровно
   один worker и проверьте сохранённый baseline/доставку. Не запускать SQLite и
   PostgreSQL worker одновременно. Оставьте исходный backup по политике retention.

## Воспроизведение тестов

```bash
uv sync --frozen --extra dev
uv run --frozen --extra dev python tools/test_postgres.py
```

Нужен доступ к локальному Docker socket и образ `postgres:17` (при необходимости
сначала pull). Runner создаёт новый сервер с одноразовым тестовым паролем, публикует
порт только на `127.0.0.1`, использует случайные схемы, запускает тесты, затем
перезапускает сервер и отдельными процессами проверяет восстановление pending
очереди/курсора/дедупликации. Созданные контейнер/volume/сеть удаляются в finally.
Личные DSN, токены и сообщения ему не нужны. Обычный `pytest` без `TEST_POSTGRES_URL`
явно пропускает PostgreSQL cases; такой запуск не доказывает поддержку PostgreSQL.
