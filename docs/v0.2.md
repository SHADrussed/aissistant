# v0.2: расширенный мониторинг, приватность и лимиты

Выпуск подготовлен для review. Merge, deploy и включение live не выполняются
автоматически. Synthetic остаётся режимом по умолчанию, без внешних API.
Полный безопасный пример: `config/default.toml`. Старый TOML продолжает работать;
новые параметры получают defaults. Проверяйте итоговую конфигурацию перед live.

## Telegram: explicit и all

`telegram.mode="explicit"` сохраняет числовой `allowed_chat_ids` и runtime
`TELEGRAM_PEER_HASHES` выбранных peers. Даже здесь применяются исключения.
`excluded_chat_ids` — signed IDs; `excluded_chat_types` — `private`, `bot`,
`group`, `supergroup`, `channel`. В примере по умолчанию исключены bot/channel.
`private` — личный диалог с человеком; `supergroup` — megagroup.
Исключённые чаты не читаются через историю; metadata может прийти в GetDialogs.

Включение `all` расширяет область чтения и требует отдельного решения владельца.
Не включайте его только ради проверки бота. Для будущего включения нужны:

```toml
[telegram]
enabled = true
mode = "all"
confirm_all = true
excluded_chat_ids = [] # заполните локально; реальные IDs не коммитьте
excluded_chat_types = ["bot", "channel"]
batch_size = 100
discovery_recent_limit = 100
discovery_max_dialogs = 5000
discovery_refresh_seconds = 86400
```

И одновременно runtime `ALLOW_TELEGRAM_ALL=true`, обычные `ALLOW_LIVE_READS=true`
и `ALLOW_AI_PROCESSING=true`, `mode="live"`, уже подготовленные Telegram session,
бот, OpenAI и постоянная БД. Утилита личной авторизации остаётся только на личном
устройстве. StringSession не сохраняется в БД или файлах; для all peer access_hash
получается из GetDialogs и кэшируется в защищённой БД, не в Git/TOML/логах.

Сразу после подключения выполняется ограниченный проход metadata диалогов
(включая архивные, если их возвращает Telegram), максимум discovery_max_dialogs.
Далее каждый цикл просматривает только первые discovery_recent_limit диалогов;
ограниченный полный refresh повторяется по discovery_refresh_seconds, а не
каждые 15 минут. Кэш и время refresh переживают restart. FloodWait discovery
сохраняется отдельно от FloodWait конкретного чата. Отказ discovery не отменяет
обработку уже известных чатов. Saved Messages и собственный бот уведомлений
исключаются; сообщения от него внутри других чатов также пропускаются.

Это polling, не подписка на updates: новые активные чаты обычно появляются
в ближайшем recent проходе, тихие/архивные — при полном refresh. При количестве
диалогов больше discovery_max_dialogs покрытие неполное: увеличьте предел
осознанно или используйте explicit. Порядок pinned/folders зависит от Telegram.
Недоступные удалённые peers могут оставаться в кэше; исключите их ID при отзыве доступа.

Для нового peer сохраняется последний известный ID как baseline; история до
него не классифицируется. API metadata может содержать последнее сообщение, но
его текст не анализируется/не сохраняется. Существующие курсоры не заменяются
новым baseline ни при restart, ни при смене режима. Возврат ранее исключённого
чата возобновляет чтение после сохранённого cursor, включая накопившийся backlog.

## Gmail: inbox и all_mail

`gmail.mode="inbox"` требует INBOX плюс остальные label_ids.
`gmail.mode="all_mail"` снимает только обязательный INBOX; другие label_ids
остаются фильтрами. Чтобы читать всю новую входящую почту, можно задать
`label_ids=[]`. SENT/DRAFT/SPAM/TRASH всегда исключены, независимо от режима.

Обрабатываются только messageAdded после сохранённого historyId: новое письмо,
уже архивированное до poll, также проходит all_mail. Архивирование старого письма
через labelsRemoved не запускает его анализ. messages.list и поиск старых писем
не используются. При первом подключении сохраняется текущий historyId без backfill.
При смене режима cursor не сбрасывается; ранее пропущенные/seen письма не
переанализируются. Это намеренно не средство импорта старой почты.
Readonly OAuth и проверка единственного gmail.readonly scope сохранены. Истёкший
history по-прежнему требует ручного решения владельца; автоматического rebaseline нет.

## Локальные фильтры и личные переписки

Перед любым OpenAI запросом применяются:

- `privacy.excluded_chats`: scope или `source:scope`, например `telegram:-123`.
- `privacy.excluded_senders`: строковый Telegram sender ID или Gmail From address
  (адрес приводится к lowercase; display name не участвует). From может быть подделан.
- `exclude_keywords`: подстроки без учёта регистра, до обрезки текста.
- Эвристики OTP/кодов, password/API token/refresh token присваиваний, известных
  ключей, JWT, private key заголовков и формата bot token. При срабатывании
  сообщение целиком исключается; raw text и секрет не попадают в сводку/логи.

**Фильтры не гарантируют обнаружение всех чувствительных данных.** Возможны
пропуски и ложные срабатывания; они не заменяют согласие, allowlist, ограничение
источников или проверку политики провайдера. Вложения/HTML не анализируются.
В БД остаётся только dedup hash для исключённого сообщения.

Для private/bot/неизвестного типа Telegram применяется `private_chat_policy`:
`local_only` по умолчанию создаёт Low карточку без содержимого: «Новое личное
сообщение», ссылка/идентификатор для ручного открытия. `skip` исключает полностью.
`allow_ai` явно разрешает передачу содержимого модели после остальных фильтров.
`privacy.personal_gmail_senders` позволяет применить то же правило к выбранным
личным отправителям Gmail. Нельзя надёжно распознать «личное письмо» до анализа
по одному From; Gmail без этого списка подчиняется общим локальным фильтрам.
Группы, даже небольшие, не считаются private автоматически: добавляйте их в исключения.

## Приоритеты и защита от потока

OpenAI возвращает enum `critical`/`important`/`low` в структурированном ответе.
Ошибки/галлюцинации приоритета возможны. Synthetic classifier остаётся
детерминированным fixture classifier, существующие fixtures имеют Important;
все три уровня отдельно покрыты синтетическими unit/integration cases.

- Critical отправляется сразу после классификации, не ожидая завершения poll
  остальных чатов или digest. «Сразу» означает при обработке очередного poll,
  а не realtime: частота чтения остаётся poll_seconds и ограничивается schedule.
- Important собираются в компактные группы раз в digest_seconds (по умолчанию
  900), первый digest после обновления/первого старта может уйти сразу.
- Low сохраняются без автоматической отправки. Владелец может запросить их
  вручную из runtime: `/app/.venv/bin/aissistant --request-low`. Команда не poll-ит
  источники; она требует эксклюзивной блокировки БД, поэтому сначала остановите
  основной worker, используйте maintenance container с той же БД, затем верните
  обычный запуск. Не запускайте второй worker параллельно и не удаляйте volume.
  На Railway безопаснее выделить maintenance window, если нет одноразового job
  с доступом к тому же storage. Команды Telegram-бота не добавлены.

Лимиты notifications.max_per_cycle, max_per_hour и digest_max_items ограничивают
отправку. Текст группы ограничен размером Bot API. Часовое окно сохраняется в БД;
restart не снимает лимит. Critical имеет преимущество, но также подчиняется лимиту.
Переполненная очередь остаётся pending. Ошибка отправки прекращает отправки до
следующего цикла; автоматических повторов внутри того же цикла нет.
Доставка остаётся at-least-once: неопределённый результат HTTP/commit допускает дубль.
Low (включая незапрошенные) хранятся retention_days, затем payload удаляется,
seen остаётся. Важные/critical pending автоматически не удаляются.

## Запросы, токены и бюджет

В `[ai]` настраиваются max_requests_per_day, max_requests_per_cycle,
daily_budget_usd, max_output_tokens и цены input_usd_per_million /
output_usd_per_million. Установка любого соответствующего лимита в 0
безопасно прекращает новые API запросы; приватные local_only карточки и уже
созданные уведомления продолжают обрабатываться.

Перед запросом транзакционно резервируется консервативная стоимость: UTF-8 bytes
текста + system/schema + запас framing, полный max_output_tokens. Счётчик попыток
увеличивается до HTTP; SDK retries отключены. Даже timeout/ошибка/падение процесса
не освобождает резерв — неизвестный счёт провайдера не считается нулевым.
Ответ usage добавляет фактические input/output tokens и расчётную стоимость.
Резерв намеренно не уменьшается после успеха: это может остановить обработку
раньше фактического расхода, зато ошибочные запросы не обходят лимит.

Лимиты считаются за день UTC (начало в 03:00 по Москве); счётчики и резервы
сохраняются в api_usage и не сбрасываются после restart. При исчерпании нет
fallback в OpenAI/другую модель и нет потери сообщения: seen не выставляется,
курсор не проходит непринятое сообщение. Gmail может повторить окно; seen убирает
повторы. Содержимое deferred сообщения заново читается из источника позже,
поэтому удалённое к тому времени сообщение восстановить невозможно.

Расход — оценка по тарифам конфигурации, не счёт OpenAI. Цены-примеры не являются
подтверждёнными актуальными тарифами; проверьте model и ставки у провайдера.
Установите отдельный project budget/alerts в OpenAI: скрытые provider расходы,
изменение тарифов, другие приложения/ключи вне контроля этого worker.
Сравнение с бюджетом использует целые micro-USD, без float. Просмотр сегодняшних
счётчиков без содержимого и credentials: `aissistant-db usage`, с заранее заданным
runtime MIGRATION_DATABASE_URL нужной БД. Значения DSN в команду/чат не вставляйте.

## Обновление и rollback

1. До merge ознакомьтесь с PR/зелёными CI checks; deploy только после подтверждения.
2. Остановите worker и создайте защищённый backup/snapshot SQLite volume или PG.
3. Запустите `aissistant-db upgrade` с runtime MIGRATION_DATABASE_URL. Либо при
   одобренном deploy worker выполнит upgrade под своей эксклюзивной блокировкой.
4. Миграция 0002 добавляет priority=important прежним outbox строкам и новые
   telegram_peers/api_usage таблицы. Не меняет payload, delivered, seen или cursor.
   Новые таблицы включены в offline SQLite → PostgreSQL copy и fingerprint check.
5. Сначала проверьте synthetic на отдельной БД: 5 fixtures один digest, затем 0,
   restart без повторов. Worker logs по-прежнему считают sent в карточках, а не
   в HTTP sendMessage запросах. Проверяйте версию schema 0002_monitoring.
6. Не используйте старый бинарник с новой БД для rollback; восстановите backup
   вместе с прежней версией кода. Downgrade с удалением данных не разрешён.
7. Live, all, приватная передача AI и права аккаунтов включаются отдельно владельцем.
   Конфигурацию в PR не заполняйте личными IDs, sender addresses или секретами.
