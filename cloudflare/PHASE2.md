# Фаза 2: защищённый MCP для чтения и поиска — проект, не реализация

Начать отдельным PR только после успешного контролируемого **реального** webhook
на метаданных, проверки владельца/allowlist, повторной доставки и перезапуска с
тем же D1 binding. Затем получить отдельное решение владельца о хранении текстов
и перечне разрешённых потребителей. Фаза 1 продолжает работать без текстов.

## Разделение компонентов и разрешений

- Отдельный MCP Worker, отдельный hostname и отдельная конфигурация. Токен бота и
  webhook secret ему не передаются. Никаких Telegram write API и OpenAI API.
- HTTPS MCP с проверенной OAuth 2.1 авторизацией: доверенный issuer, audience,
  подпись, срок действия, PKCE для публичного клиента, отзыв доступа. Cloudflare
  Access можно использовать как дополнительный барьер, но не считать его автоматически
  совместимым с OAuth/MCP-клиентом. Совместимость проверить до выбора механизма.
- Два независимых права: `archive:read` и `archive:search`; по умолчанию нет ни одного.
  Отдельные гранты на owner, connection и chat ID, срок разрешения и лимиты выдачи.
  Авторизация проверяется на каждом запросе, включая пагинацию и получение по ID.
  Нельзя принимать owner/chat scope от клиента без пересечения с серверными грантами.
- Только методы `get_message`, `list_messages`, `search_messages` с ограничениями
  периода, числа результатов, длины запросов и rate limit. Нет произвольного SQL,
  команд, отправки, редактирования, удаления сообщений или изменения разрешений.
- Управление разрешениями, retention и удалением — отдельный административный
  интерфейс с сильной аутентификацией, не MCP tools. Отзыв доступа немедленно
  прекращает чтение; аудит хранит ID операции/клиента, но не текст и токены.
- D1 binding не даёт таблицам SQL read-only ACL. Для технического разделения нужен
  приватный сервис чтения с ограниченным RPC либо отдельное хранилище/реплика:
  MCP Worker не получает произвольный доступ на запись к ingestion DB. Выбрать
  и проверить этот механизм в следующем дизайне, не полагаться лишь на названия tools.

## Осознанное хранение текстов

Отдельный opt-in по чатам и подключениям, выключенный по умолчанию. Только новые
события после согласия, без backfill. Текст хранится в отдельной таблице/базе с новой
миграцией; метаданные и дедупликационные ключи фазы 1 сохраняются. Перед записью
локальные фильтры секретов/OTP и личных данных. Фильтры не гарантируют обнаружение
всех чувствительных данных. Вложения не скачиваются автоматически.

Владелец задаёт срок хранения, максимальный размер, допустимость поиска/индексации,
правила очистки, экспорта и удаления. Удалять также поисковый индекс; учитывать
D1 backups/Time Travel и срок их сохранения. Определить модель шифрования и ключей:
полнотекстовый поиск по шифротексту не работает как обычный FTS, нельзя обещать
одновременно E2E-шифрование и серверный поиск без отдельного решения.

Сообщения — недоверенные данные, в том числе инструкции для ИИ. Возвращать их с
границами и происхождением; никогда не исполнять указания из переписки и не
разрешать им менять scopes. Читающий MCP-клиент может передать текст своему
провайдеру модели: владелец отдельно разрешает конкретного клиента и такую передачу.

## Обязательные проверки перед выпуском фазы 2

1. Нет авторизации, просроченный/чужой токен, неверный audience и отозванный grant:
   нет доступа к данным, включая IDOR, search, курсоры и ошибки.
2. Изоляция владельцев/чатов, SQL/search injection, лимиты, пагинация и одновременный
   отзыв разрешений. Поиск не раскрывает существование запрещённых сообщений.
3. Opt-in, отсутствие скрытого backfill, retention и удаление текстов/индекса,
   миграция без потери дедупликации и restart recovery.
4. Отсутствие write tools, токенов бота в MCP, тел запросов в логах, обходов через
   prompt injection и передачи информации неразрешённому клиенту.
5. Совместимость настоящего MCP-клиента с OAuth и протоколом; отдельная ручная
   проверка в тестовом аккаунте после разрешения владельца.
