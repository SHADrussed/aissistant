# aissistant — личный ИИ-секретарь v0.2

MVP фонового worker на Python 3.12: каждые 15 минут анализирует новые сообщения
из явно разрешённых Telegram-чатов и Gmail, выделяет клиентов/заказы, деньги,
срочные вопросы, учёбу, личное и другое. Формирует краткие сводки, договорённости,
рекомендации и черновики; отдельный Telegram-бот доставляет их владельцу.
**Ответы собеседникам не отправляются.**

## Безопасный запуск без личных данных

Нужны Python 3.12 и uv. Из корня репозитория:

```bash
export UV_CACHE_DIR=/workspace/.cache/uv # в Codex; локально можно не задавать
uv sync --frozen --extra dev
uv run --frozen aissistant --once
uv run --frozen aissistant --once
uv run --frozen --extra dev pytest -q
uv run --frozen --extra dev ruff check .
```

Первый запуск: `sent=5 success=True`; второй: `sent=0 success=True`.
Пять карточек Important группируются в один digest; `sent` считает карточки.
Это встроенные вымышленные сообщения, локальный детерминированный классификатор
и локальный приёмник, без API и без отправки ботом. В stdout только счётчики.
Low запрашиваются отдельно через `--request-low` при остановленном worker.
Сводки можно посмотреть локально в `.data/synthetic.db`, таблица `outbox`.
`--once` возвращает 0 при успешном цикле, 1 при ошибке, 2 вне расписания.
Без `--once` запускается постоянный worker; SIGTERM/SIGINT завершают его после
текущих операций. Настройки читаются при старте; после изменения нужен restart.

```bash
docker build -t aissistant:mvp .
docker run --rm --network none -v aissistant-test:/data aissistant:mvp /app/.venv/bin/aissistant --once
```

Railway использует основной `Dockerfile` без secret mounts. Для сборки за TLS-прокси
Codex предназначен отдельный `Dockerfile.codex`; команды в [проверках](docs/validation.md).

Оба режима используют постоянное состояние. Для нового синтетического прогона
можно выбрать другой `SYNTHETIC_DATABASE_URL` или удалить только тестовую БД.
Нельзя сбрасывать live-БД для обычного перезапуска.

## Настройки

`config/default.toml` — полный безопасный пример. Для live скопируйте его в
игнорируемый `config/local.toml`; путь задаётся `ASSISTANT_CONFIG` или `--config`.
Для Railway можно вместо файла задать полный многострочный TOML в
`ASSISTANT_CONFIG_TOML`. Не совмещайте его с `ASSISTANT_CONFIG`/`--config`.
В TOML нет секретов. `.env.example` перечисляет имена; приложение **не загружает
.env автоматически**, переменные должны быть переданы процессу runtime.

| Настройка | Значение |
|---|---|
| `mode` | `synthetic` по умолчанию; `live` требует отдельного opt-in |
| `poll_seconds` | 900; интервал между завершением цикла и следующим циклом |
| `telegram.enabled` | По умолчанию false |
| `telegram.mode`, `telegram.allowed_chat_ids` | `explicit` и числовой allowlist по умолчанию; `all` требует двойного opt-in |
| `privacy.private_chat_policy` | `local_only`: личное содержимое не передаётся OpenAI |
| `notifications` | Интервал digest, лимиты отправок за цикл и час |
| `ai` | Лимиты запросов, суточный бюджет, цены, предел вывода |
| `telegram.batch_size` | До 100 новых сообщений каждого чата за цикл, от старых к новым |
| `gmail.enabled`, `gmail.label_ids` | По умолчанию false; все указанные метки должны присутствовать, обычно `INBOX` |
| `notify_categories` | Какие категории включать в уведомления |
| `exclude_keywords` | Исключение по подстроке без учёта регистра перед передачей модели |
| `schedule` | IANA timezone, дни 0–6, начало включительно, конец исключительно |
| `max_text_chars` | 12000; обрезка до передачи модели |
| `retention_days` | 7 дней для доставленных сводок |
| `ai.model` | `gpt-4o-mini`, модель с поддержкой structured outputs |

Для ночного интервала задайте полный день или измените реализацию: диапазон через
полночь намеренно не принимается валидатором. Вне расписания worker не читает
источники и не отправляет outbox; в следующий разрешённый цикл обработает backlog.

## Подключение реальных интеграций — только после отдельного решения владельца

В Codex личная авторизация не выполнялась. Следующие шаги — инструкция владельцу,
а не утверждение о проверенных интеграциях. Не включайте live без согласия на
чтение и передачу содержимого OpenAI и отдельному боту.

1. Создайте личное приложение на my.telegram.org на доверенном устройстве.
   Там же, **вне Codex**, локально авторизуйте Telethon и получите StringSession.
   Это полноценный ключ доступа к аккаунту: сохраняйте его только как runtime
   secret `TELEGRAM_SESSION`. Не создавайте `.session` в репозитории или volume.
   Worker использует только `connect` и проверяет существующую авторизацию;
   просить телефон, код или пароль он не умеет.
2. На доверенном устройстве выберите конкретные Telegram chat IDs. Для личных
   диалогов и supergroups/channels получите access_hash выбранных peers той же
   учётной записи и передайте secret `TELEGRAM_PEER_HASHES`: JSON-объект
   `{"<signed chat id>": <integer access_hash>}`. Для обычных групп hash не нужен.
   Worker не перечисляет все диалоги ради поиска hash. Не публикуйте реальную карту.
3. Создайте отдельного бота через BotFather, отправьте ему `/start` от владельца,
   задайте `TELEGRAM_BOT_TOKEN` и положительный `TELEGRAM_OWNER_CHAT_ID`.
   При отправке проверяется, что это private chat. Бот не принимает команды,
   получателя нельзя изменить текстом сообщения или выводом модели.
4. В Google Cloud включите Gmail API и настройте OAuth consent + Desktop client.
   На доверенном устройстве выполните установленный OAuth flow с offline access
   и **единственным** scope `https://www.googleapis.com/auth/gmail.readonly`.
   Передайте `GMAIL_CLIENT_ID`, `GMAIL_CLIENT_SECRET`, `GMAIL_REFRESH_TOKEN` через
   runtime secrets. Если выдавались более широкие scopes, отзовите grant и
   авторизуйтесь заново: worker проверяет фактический scope через tokeninfo.
   Не коммитьте client JSON и token JSON. В режиме Google OAuth Testing refresh
   tokens могут истекать через 7 дней; учтите требования Google для production.
5. Передайте `OPENAI_API_KEY`. Проверьте политику хранения/обработки данных у
   провайдера; `store=false` не означает универсальное отсутствие всех журналов
   провайдера. Не используйте чужие сообщения без необходимого согласия.
6. Укажите `LIVE_DATABASE_URL=sqlite:////data/secretary.db` для persistent volume
   или `postgresql://...` (SQLAlchemy использует psycopg). Для внешнего PostgreSQL
   настройте TLS по требованиям провайдера, например `sslmode=verify-full` с CA.
   Для схемы используется Alembic; старый MVP принимается без перезаписи данных.
   Offline-перенос SQLite → PostgreSQL выполняет `aissistant-db copy --confirm-offline`,
   только с остановленными worker и пустой целью; [процедура](docs/database-migrations.md).
7. Только после подтверждения: `mode="live"`, enabled нужных источников,
   allowlist; runtime `ALLOW_LIVE_READS=true`, `ALLOW_AI_PROCESSING=true`.
   Запуск: `uv run --frozen aissistant --config config/local.toml --once`.
   Первый цикл устанавливает baseline, старую переписку не анализирует.
   Затем создайте контролируемое новое сообщение в разрешённом источнике и
   запустите следующий цикл; вручную проверьте сводку и отсутствие автоответа.

Можно включить только Gmail или только Telegram. Для выключенного источника его
секреты не нужны. Бот и OpenAI обязательны для любого live-источника.
Фильтрованное/уже обработанное сообщение не будет переанализировано после смены
фильтров. Удаление чата из allowlist прекращает чтение, но ранее созданный outbox
продолжает доставляться. Для удаления этих результатов остановите worker и
удалите данные согласно вашей политике хранения.

## Надёжность и границы MVP

- Состояние и outbox записываются транзакционно. Сбой модели не помечает сообщение
  обработанным. Сбой бота сохраняет pending для следующего цикла. Ошибки одного
  источника не блокируют остальные; отдельные Telegram-чаты тоже изолированы.
- Telegram baseline — последний ID при первом включении каждого чата. Gmail
  baseline — `historyId` профиля. Gmail history полностью пагинируется, scope
  проверяется при обновлении access token. SENT/DRAFT/SPAM/TRASH не анализируются.
  Истёкший Gmail history (404) не сбрасывается автоматически: в логах будет
  `gmail_history_expired_manual_rebaseline_required`. После восстановления доступа
  владелец должен решить, как обработать пропущенный период; удаление только
  курсора `gmail:history` с остановленным worker создаёт новый baseline и
  **пропускает** этот период. Смена Gmail-аккаунта требует отдельной БД.
- Critical доставляется при обработке, Important группируются по расписанию,
  Low — по ручному запросу. Действуют лимиты отправок за цикл и час. Реальная сводка не выводится в логи. Для личного Telegram-диалога
  универсальной HTTPS-ссылки нет — это явно указано в карточке; для supergroup/
  channel используется `t.me/c`, Gmail — ссылка на исходное письмо.
- Удаления/редактирования, вложения и HTML-only body не анализируются (тема письма
  остаётся). Медиа без текста пропускается. Нет web UI, команд бота, многопользовательского
  режима и распределённой обработки очереди; **ровно одна реплика** обязательна.
  Второй worker той же БД отказывает: SQLite flock / PostgreSQL session advisory lock.
- Доставка at-least-once: при потере подтверждения Bot API/commit возможен повтор.
  Seen хранится после очистки доставленных сводок. Недоставленные Important/Critical не удаляются
  автоматически (Low истекает по retention_days): следите за объёмом БД и доступностью бота. Удаление payload логическое;
  старые страницы SQLite/backup требуют отдельной безопасной политики удаления.
- Не храните личные данные в Git, логах, Docker build context или образе. Для БД,
  snapshots и backups нужны ограничение доступа и шифрование на стороне оператора.
  Черновики — предложения модели: проверяйте факты, даты и обязательства вручную.
- PostgreSQL 17, миграции и сохранение pending очереди после перезапуска проверены
  на одноразовом локальном сервере; `uv run --frozen --extra dev python tools/test_postgres.py`.
  Telegram/Gmail/OpenAI и deploy v0.2 остаются непроверенными; владелец подтвердил
  получение отдельного тестового уведомления ботом на предыдущей версии.
  API contract-тесты используют fake transports; [текущий отчёт](docs/deployment-audit.md).

## Диагностика

Логи содержат фиксированные коды и счётчики; исключения SDK намеренно не печатаются,
поскольку могут содержать токены и личный текст. `startup_or_storage_failed_check_configuration`
означает: проверьте TOML, наличие переменных (не значения в логах), права на БД и
runtime. `source_poll_failed` — доступ, квоты, авторизация или обработка источника;
`notification_failed` — доставка боту. Не включайте debug SDK/HTTP в production.
Повторные сетевые попытки OpenAI/Telethon ограничены; FloodWait сохраняется в БД,
Bot API соблюдает retry_after и ограничивает отправку примерно одной карточкой в секунду; Gmail/Bot API повторяются
на следующем цикле, без горячего retry-loop. Для расследования используйте
контролируемые тестовые аккаунты, не дампите секреты и сообщения.
